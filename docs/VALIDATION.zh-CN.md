# 合并验证，减少重启

[English](VALIDATION.md)

| 阶段 | 合并执行的检查 | 必须达到的结果 |
|---|---|---|
| 在线准备 | 固件/IFR、PCI拓扑、IOMMU、地址上限、备份和救援文件 | 准确版本审核及备份完整性通过 |
| 首次USB启动 | 只读CHECK、保存变量，再启动PVE救援 | USB引导器/内核/initrd能启动原PVE根系统 |
| 改动会话 | CHECK、完整变量往返测试，再APPLY | 测试完整恢复原值；应用仅改变计划字节 |
| 改动后PVE启动 | 变量差异、根窗口、手动调整、单VM测试、安装服务 | 主客机检查通过后才启用自动化 |
| 最后正常重启 | 服务日志、启动顺序、主客机复核 | 从固件默认大小实际调整，且先于PVE客机启动 |

从准备完成的宿主开始，通常是 **2 次 USB Shell 启动 + 3 次 PVE 启动**（PVE 救援、改动后的 PVE、最后正常重启），另加可选的冷恢复菜单测试。恢复菜单入口未核实时，在改动会话前单独验证。相关 F2 设置一次记录；退出 F2 可能额外触发重启。现场应有可用控制台。

## 验收项目

- **宿主：**变量仅改变已审核字节；根MMIO符合CPU地址上限并容纳对齐的目标BAR；各级桥覆盖BAR；其他BAR大小不变；VFIO恢复绑定；存储、引导和内存正常。
- **客机：**每块实体GPU一次只测一台VM。检查目标BAR、AMDGPU绑定、全部可用显存可见、`/dev/kfd`、ROCm识别及小规模HIP分配/写入/读回。BAR大小不必等于可用显存数值。
- **持久化：**检查本次启动日志及相对`pve-guests.service`的顺序。BAR已经变大时启动服务，只能证明无需调整的路径。
- **恢复：**区分文件检查、实际USB/救援启动、恢复菜单入口及真正刷写恢复；它们证明的能力不同。

将`guest_check.py`与`rebar_audit.py`放在客机同一目录：

```sh
sudo python3 -B guest_check.py --hip-test
```

没有`--hip-test`就不分配测试显存。带超时等待AMDGPU和VRAM就绪；guest agent能响应并不足够。

## 实用检查

- 使用直接的`qm status` / `pct status`和实际QEMU/VFIO占用；PVE集群摘要可能滞后。
- FAT32文件名不能含冒号。只处理备份文件名，不能改变传给sysfs的PCI地址。
- 在`noexec`挂载上显式调用Python，不降低挂载保护。
- 将ESP备份解压为U盘普通测试文件，核对原始哈希并对该文件运行`fsck.fat -n`；不能覆盖正常ESP来演练。
- 将恢复包校验并还原到新的FAT32 U盘，核对文件哈希，再测试F12 → UEFI U盘 → Shell → PVE救援。解压成功不能证明可启动。

实际结果和命令输出留在私有仓库。固件、拓扑或救援内核变化后，重新执行相关检查点。
